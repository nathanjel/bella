## Problems in the drafted words

* D-33 'CPython's import of a module not yet in sys.modules looks up a lock': CPython also looks one up for a module that is in sys.modules and still initialising. That happens through import.c's ensure_initialized -> _lock_unlock_module (an import statement in a circular import, or `import pkg.sub` in pkg's body), through _resolve_parents -> _lock_unlock_module(ancestor), and through _find_and_load's initialising branch at line 1313 (importlib.import_module, importlib.__import__). Measured by p7_pkg, p8_circ, f2_eq, f11_reentry and modc.
* D-33 'has its __hash__ called there': this undercounts, and it omits calls that come later and calls that are not __hash__. There are 2 calls in _get_module_lock when it makes the lock (lookup at line 438, store at 459), or 1 when a live lock exists (f1_hash, kept exception). There are 2 more in cb (lines 454-455) when the lock dies. That is at _find_and_load's end after a success or ModuleNotFoundError; when the exception is released after a body raised (end of the except clause, del, or inside gc.collect() for cyclic garbage); and never if that exception is kept to the end of the program. They run with _imp.lock_held() True. There is also __eq__ on a stored key whenever another name object with the same hash meets it (equal names: a package's name during its submodules' imports, circular imports; unequal names with a custom __hash__).
* D-33 'a name that is a str subclass': only __import__, importlib.__import__, _gcd_import and __lazy_import__ (at first use) hand the object to the lock. importlib.import_module slices it to an exact str, and no S method is called at all (p6_none: 0 calls). The __eq__ calls also fall on another module's name, the key an outer import stored, not on the name being imported.
* D-33's list names 11 names, but 14 stop with D-33's message (ABSENT_BY_ENTRY, runtime/src/call.cpp:1849-1856, also has _List, _thread and _weakref). Two classes reachable without a name are not named: _WeakValueDictionary.__init__.<locals>.KeyedRef, which weakref.ref.__subclasses__() lists, and cb, which unraisable reports name. 'stops the program with a message naming D-33' holds for reading the names. dir()/vars()/__dict__ of _frozen_importlib and __subclasses__() of a built-in type stop with other messages (imports.cpp:1416, types.cpp:1479, read).
* D-33 'The import system takes no module locks': it also takes no global import lock. CPython holds _imp's lock inside _get_module_lock, cb and the finder loop's _ImportLockContext (_find_spec), so _imp.lock_held() is True there. The runtime's is False throughout an import (runtime/prelude/_imp.py:105). _ImportLockContext is that global lock around the finder, not a module lock, and its absence follows from the closed world's finder as much as from one thread.
* D-33 lists the stopped names and the two code objects, but _lock_unlock_module itself does not stop. It exists and ignores its argument (no TypeError for an unhashable one, no hash calls), which the words do not say.
* D-33 says nothing about the lock machinery's weakref callbacks (cb, KeyedRef.remove), which CPython runs as callbacks. What fails inside them is swallowed and reported as 'Exception ignored while calling weakref callback ...': a __hash__ that raises, a RecursionError when a failed import's exception is dropped at the limit, a raising signal handler.
* D-17 'the frames CPython's import system enters and leaves before a module's body runs (... its module locks ...)': the lock frames also run where no body runs. An import that finds its module initialising runs _lock_unlock_module -> _get_module_lock -> acquire -> __enter__ -> setdefault -> KeyedRef: 5 frames under an import statement, 7 under importlib.import_module, with the RecursionError in setdefault. They also run after the body: cb, at _find_and_load's return or whenever a failed import's exception is released, at any depth the program chooses (an unraisable RecursionError at headroom 0).
