# L2: the typed, ANF, lifetime-explicit level (v1, reviewed by the author on 2026-11-02)

Status: v1, the grammar the L1-to-L2 passes are written against (TODO tasks 3 and 4; design section 8;
review log D-2, RL-20, RL-49). The design asks that grammars be reviewed before their passes are
written: the author answered the six questions of v0 on 2026-11-02, and section 8 records the
answers (`docs/DECISIONS.md`, 2026-11-02). Implemented the same day: `pipeline/l2/` (section 7).

## 1. Where L2 sits, and what it adds

```
Python ─frontend passes─▶ L1 (PyCore) ─L1→L2 passes─▶ L2 ─(later: L3, L4)─▶ C++ ─GCC─▶ binary
                          eval1                        eval2
```

L1 is desugared Python: every construct is a small core node, but names are still resolved the
way Python resolves them at runtime (eval1 walks scopes), expressions still nest, and nothing says
when an object dies. C++ needs all three made explicit. L2 makes each one a property of the tree:

| L1 leaves implicit | L2 states explicitly |
| --- | --- |
| How a name is found (scope walk at runtime) | Every name access is one of six kinds (section 3), as CPython's compiler decides with its symbol table |
| The order of evaluation inside an expression | A-normal form: every intermediate value is a named temporary, assigned once, in Python's left-to-right order |
| What an operator does | Every operation is a named protocol operation with CPython's semantics (`binary(+)`, `getattr`, `for_next`, ...) |
| When a reference is dropped | `release` statements at the points where CPython drops the reference, so finalisers and weak-reference callbacks happen when they happen under CPython (spec section 9) |
| What a value is | Each place has a type slot; in phase 1 it is always `object` and every value is represented boxed (`Obj`); the oracle's types are a marked gap until phase 2 (section 8, decision 3) |

The design's level table puts types from the oracle, ownership and C++ intent at L2, L3 and L4.
Phase 1 is "everything boxed and exact; speed is phase 2's job" (design section 11), so L2 v1
carries the type slot only, always `object`, and emits C++ directly; L3 and L4 come with phase 2.
**Gap, marked:** the design's level table says every L2 expression carries a type from the oracle.
L2 v1 does not. The gap closes in phase 2, when a pass produces `Fact.TYPES` (no pass produces it
today, so no pass can require it); until then a declared type must not change what a program does
(section 8, decision 3).

## 2. Principles

1. **Small core, passes in front** (the author, 2026-11-02). L2 adds no Python feature: every
   feature reached L1 through a desugaring pass. L1→L2 passes only make things explicit.
2. **CPython's machine, not CPython's code.** Name kinds, the evaluation order and the release
   points follow what CPython's compiler and eval loop do, read from the pinned 3.15.2 sources;
   the operations are implemented by Bella's runtime, not by calling CPython.
3. **One meaning per node.** A statement performs at most one operation. Control flow is
   structured (if, loop, try), never goto, so the C++ stays readable and the proofs stay local.
4. **Checkable at every step.** `wf2` checks the invariants, `eval2` executes L2, and every
   L1→L2 pass is tested by `eval1(x) == eval2(P(x))` on the corpus and the three targets, as the
   frontend passes are tested today. A printer renders L2 the way `pipeline/l1/pretty.py` renders L1.

## 3. Names: six kinds, decided statically

CPython's symbol table decides, for every occurrence of a name, which instruction reads it. L2
records that decision; the `resolve-names` pass makes it, by CPython's rules (`Python/symtable.c`).

| L2 kind | CPython instruction | Where | Semantics |
| --- | --- | --- | --- |
| `local x` | `LOAD_FAST` / `STORE_FAST` | a function's own variable no inner function captures | a slot in the frame; `UnboundLocalError` if unset |
| `cell x` | `LOAD_DEREF` (own cell) | a function's variable an inner function captures | a cell object in the frame |
| `free x` | `LOAD_DEREF` (closure) | a variable of an enclosing function | the closure's cell; `NameError` (free variable) if empty |
| `global x` | `LOAD_GLOBAL` | a module-level name read from a function, or declared `global` | the module's dict, then builtins; lazy imports resolved; under P-3 an unseen name is still this kind, looked up at runtime |
| `name x` | `LOAD_NAME` / `STORE_NAME` | a class body, a module body, exec'd text with its own locals | through the namespace mapping, then globals, then builtins |
| `classdict x` | `LOAD_FROM_DICT_OR_GLOBALS` / `..._OR_DEREF` | annotation scopes and PEP 695 scopes in a class | the class namespace first, then global or free |

Temporaries are a seventh kind, `t1, t2, ...`, invisible to the program. L1's synthetic names
(`_comp3`, `_dec0`) become temporaries or hidden locals here.

A code object records its slot tables in CPython's order (`co_varnames`, `co_cellvars`,
`co_freevars`), because the order is observable: a frame releases its locals in reverse slot
order when it exits, last slot first (`_PyFrame_ClearLocals` in `Python/frame.c` walks down from
the stack top; on 3.15.2, locals `a, b, c` die as `c, b, a`, on return and when a traceback dies).

## 4. The grammar

As implemented in `pipeline/l2/grammar.py` (frozen dataclasses, as L1's):

```
Module    ::= code: Code                   # the module body; nested codes sit in their MakeFunction
Code      ::= name qualname kind params
              varnames cellvars freevars   # slot tables, CPython's order
              first_line body: Block
kind      ::= module | function | generator | coroutine | async generator | classbody | lambda
Block     ::= Stmt*

Atom      ::= Const | Temp                 # an operand: never a nested expression, never a name
NameRef   ::= local x | cell x | free x | global x | name x
            | classdict(mapping, then) x   # mapping: locals | __classdict__; then: global | free

Stmt      ::= Let(Temp, Op)                # one operation, its result in a fresh temporary
            | Do(Op)                       # an operation for its effect; the result dropped at once (POP_TOP)
            | Unpack(Temp*, Atom, star)    # UNPACK_SEQUENCE / UNPACK_EX; consumes the source
            | Store(NameRef, Atom)         # consumes the value; the old value is released after the store
            | Delete(NameRef)
            | Release(Temp)
            | If(Temp, Block, Block)       # consumes its bool test
            | IfEnd(Temp, Block, Block)    # whether ForNext found the end; in the first block the temporary is dead
            | Loop(Block, holds: Temp*, orelse: Block)
            | Break | Continue | EndLoop    # EndLoop: leave the loop as a failed test or an exhausted iterator does, running orelse
            | Return(Atom) | Raise(Atom?, Atom?)
            | Try(Block, Handler*, orelse: Block, finally: Block)
            | Line(n)
Handler   ::= match: Block, type: Temp?, name: NameRef?, Block   # the type is computed only when the clause is reached

Op        ::= Load(NameRef) | Copy(Atom) | Locals | CellOf(NameRef) | Builtin(name)
            | Binary(op, a, b) | InPlace(op, a, b) | Unary(op, a) | Not(a) | Truth(a) | Compare(op, a, b)
            | GetAttr(o, "n") | SetAttr(o, "n", v) | DelAttr(o, "n") | GetItem(o, k) | SetItem(o, k, v) | DelItem(o, k)
            | Iter(o) | ForNext(it)
            | Call(f, a*, kw=a*) | CallEx(f, args, kwargs?) | Runtime(intrinsic, a*, kw=a*)
            | BuildList(a*) | BuildTuple(a*) | BuildSet(a*) | BuildMap(k*, v*) | ListToTuple(l)
            | ListExtend(l, x) | ListAppend(l, x) | SetUpdate(s, x) | SetAdd(s, x)
            | DictUpdate(d, m) | DictMerge(d, m, f) | MapAdd(d, k, v)
            | MakeFunction(Code, defaults?, kwdefaults?, closure: a*, annotate?)
            | Yield(a) | YieldFrom(it)     # Yield consumes its value: the caller has it while the generator is suspended
```

Changes from the draft, all found while implementing it:

* An operand is a constant or a temporary, never a name: every name is loaded into a temporary
  where CPython loads it. The draft allowed a name where nothing can run between the load and its
  use; requiring a temporary everywhere keeps `wf2` and `eval2` simple, and the emitter can fuse
  the load back.
* `Loop` owns the temporaries it `holds` (a `for` loop's iterator) and releases them when control
  leaves it by `Break`, `EndLoop` or `Return`, after the `finally` blocks nested in the loop. A
  release written before a `return` would run before such a `finally`, and CPython pops the
  iterator only when the unwinding reaches the loop's own block (a generator used as the
  iterator would be closed too early).
* `Loop` has an `orelse` and the `EndLoop` statement, so `while ... else` and `for ... else` need
  no flag: `Break` skips `orelse`, `EndLoop` runs it, outside the loop, so a `continue` in it is
  the enclosing loop's, as in Python.
* `Copy` (COPY) gives `and`, `or` and a walrus their value, since a temporary is assigned once
  per path; `Locals` (LOAD_LOCALS) is what a class body stores in its `__classdict__` cell.
* `Yield` consumes its value. YIELD_VALUE hands it to the caller, so a suspended generator does
  not hold what it yielded.
* No `retain`: an operation borrows its operands, so a temporary may be used more than once
  (`o.x += v` uses `o` twice) and is released once, after its last use.

A name is loaded into a temporary at the point CPython loads it. Augmented assignment is the case
that shows it: `g += f()` loads `g` before calling `f`, so a call that rebinds `g` is lost (CPython
3.15.2 prints 6 for `g = 1; g += f()` where `f` sets `g = 100` and returns 5).

Every temporary and every `NameRef` has a `type` field. In phase 1 it is always `object`.

Invariants `wf2` checks (`pipeline/l2/wf.py`): every temporary is live from its `Let` to exactly one
`Release` or consumer on every path, and never used or assigned outside that span; the paths that
meet (after an `If`, at a loop's head, at a `Try`'s end) agree on what is live; what is live when a
`Return` or `Raise` leaves the code is only what the enclosing loops hold; every `NameRef` agrees
with its code object's slot tables (`name` only in a module or class body); a closure matches the
nested code's free variables; `Break`, `Continue` and `EndLoop` sit inside a loop; every type is
`object`. Before the `lifetimes` pass, `wf2` runs with `lifetimes=False` and checks only that every
temporary is assigned on every path before it is used.

## 5. Lifetimes

The rule is CPython's: whatever holds a reference owns one count, and a count is dropped at the
instruction that consumes it. L2 writes those points down.

| Who holds the reference | When CPython drops it | In L2 |
| --- | --- | --- |
| an operand of an operation | after the operation, last-evaluated operand first (`a * b` drops `b`, then `a`; a call drops its arguments last to first, then the receiver) | `release` statements right after the operation, in that order |
| a local variable | when it is rebound (the old value after the new one is stored), deleted, or when the frame ends | `store` releases the old value; frame exit releases slots in reverse slot order |
| a loop's iterator | when the loop ends, by exhaustion or `break` (`POP_ITER`) | `release` on every exit edge of the `loop` |
| an exception bound by `except E as e` | at the end of the handler (`e = None; del e`) | explicit in the handler's cleanup |
| a cell's contents | when the cell dies, or is rebound | as a local, through the cell |
| the temporaries live when an exception leaves an operation | during unwinding, newest first, before the handler runs | a rule of L2's semantics, not statements (section 8, decision 1); C++ unwinding destroys automatic objects in reverse order of construction, which is this rule |
| the locals of a frame an exception's traceback captured | when the traceback dies, not when the function exits (the traceback owns the frame) | the frame record takes the locals over during unwinding; section 8, decision 5 |

`store` and `return` *move* a temporary: they take its count over, so no release follows. A
temporary used twice is retained once more (`retain t`, rare: the frontend's own temporaries, such
as a `with` statement's manager).

Each row was run on the pinned CPython 3.15.2, not taken from memory: a script printing from
`__del__` shows the order (`a * b`: "mul, del b, del a"; `f(a1, a2, a3)`: "del a3, del a2,
del a1"; a local of a function that raised dies when the handler ends, after the handler's own
output, or later if the exception is kept; a `for` loop's iterator dies before the statement after
the loop; `f(mk(1), mk(2), boom())` prints "del 2, del 1" before the handler; a frame's locals
`a, b, c` die as "c, b, a"). The order of the
first row is new in recent CPython versions, so the pin matters here too.

How this gets checked (section 8, decision 2): `eval2` runs L2 on host objects (as `eval1` runs
L1), but keeps every temporary in a slot that its `release` really deletes and holds no other
reference. Host CPython's reference counting then frees each object exactly when L2's releases say
so, and a finaliser or a weak-reference callback fires at the L2 point. `eval2` is the first level
exact about lifetimes: `eval1` keeps no finaliser traces, since L1 says nothing about when an
object dies, so the lifetime cases (C-9: disposal order, resurrection, weak references, generators
closed on their last reference, and a generated probe for each kind of release point) compare
`eval2` with CPython directly, while every other case keeps the `eval1 == eval2` chain. A use after
a release is a static `wf2` error; a release that comes too late shows up as a finaliser running
after the statement CPython runs it in, and one that comes too early as a finaliser running before.

Three things keep `eval2` itself from hiding a misplaced release:

* A checking mode: at every `release` whose object survives, `eval2` asks the host's
  `gc.get_referrers` who still holds it, and fails if a holder is `eval2`'s own (its frames, its
  loop's locals, its tracebacks). `eval2` is a tool, not a dialect program, so E-05 does not apply.
  References on the C stack in the middle of a host call are invisible to it; they last one
  operation.
* Explicit unwinding: when an operation raises, `eval2` releases the live temporaries newest first
  and cuts its own frames out of the host traceback, which would otherwise keep every temporary
  alive until the handler ends.
* A generated probe per kind of release point (an operand, a call's arguments, a `store`, the `for`
  iterator, the `with` manager, the `except ... as` name, the load held across `g += f()`, a frame's
  locals on return and on raise), each sending a `__del__` object through it.
  `pipeline/tests/test_l2_probes.py` has 31 kinds, each run as module code and as a function body;
  all 62 match CPython. They found one bug, in L1 rather than L2: the `with` desugaring kept the
  manager, the bound `__enter__` and the value in synthetic variables until the frame ended. It
  now deletes them where CPython's stack drops them, which `eval1` gains as well.

What neither host objects nor the model would check is left to other legs: a misplaced release of
an object no finaliser or weak reference can see (unobservable by section 9; at most a memory peak),
and the reference counting inside the C++ runtime's own operations (a list drops its items last to
first, a dict first to last), which the compiled differential and the model-versus-`object.hpp`
test check (task 3).

## 6. An example

```python
def total(items: list[Item]) -> int:
    s = 0
    for it in items:
        s += it.price * it.qty
    return s
```

L2 (as the printer would show it):

```
code total(items) kind function  varnames [items, s, it]  declared: items list[Item], return int
    line 2
    store local s, 0
    line 3
    t1 = iter(local items)
    loop:
        t2 = for_next(t1)
        if is_end(t2):                 # the iterator is exhausted
            release t1                 # the iterator dies before the statement after the loop
            break
        store local it, t2             # moves t2; the previous item is released here
        line 4
        t0 = local s                   # s is loaded first, as CPython does for +=
        t3 = getattr(local it, 'price')@1
        t4 = getattr(local it, 'qty')@2
        t5 = binary(*, t3, t4)
        release t4                     # last-evaluated operand first
        release t3
        t6 = inplace(+, t0, t5)
        release t5
        release t0
        store local s, t6              # the old total is released after the new one is stored
    line 5
    return local s                     # frame exit: it, s, items released (reverse slot order)
```

And the C++ the emitter would write from it (a sketch: the runtime API is task 3's):

```cpp
Obj total(Frame& f, Obj items) {
    Local s, it;
    s = Obj::small(0);
    {                                                 // t1's scope is the loop: the iterator dies at its end
        Ref t1 = py::iter(items);
        for (;;) {
            Ref t2 = py::for_next(t1);
            if (py::is_end(t2)) break;
            it = std::move(t2);                       // stores the new item, then releases the old one
            Ref t0 = s;
            Ref t3 = py::getattr(it, S_price, cache_1);
            Ref t4 = py::getattr(it, S_qty, cache_2);
            Ref t5 = py::binary_mul(std::move(t3), std::move(t4));   // consumes both: drops t4, then t3
            s = py::inplace_add(std::move(t0), std::move(t5));
        }
    }
    return s;                                         // locals released in reverse slot order on the way out
}
```

The C++ is readable because L2 already fixed the evaluation order and the release points: no
lambdas forcing an order (the toy emitter needs them today), and every release is either a scope
L2's releases delimit or an operation that consumes its operands. A `release` right after an
operand's last use becomes a move into the operation, which drops its inputs in CPython's order
itself; the emitter never relies on the order in which C++ destroys parameters or temporaries,
because that order is implementation-defined.

## 7. The passes from L1 to L2

Each pass has a `PassSpec`, with tests discharging it as the frontend passes are discharged.
As implemented (2026-11-02):

1. `resolve-names` (`pipeline/l2/resolve.py`) is the analysis `to-anf` runs first: CPython's
   symbol-table rules over L1, giving each name occurrence its kind and each code object its slot
   tables, including the implicit cells `__class__` and `__classdict__`. Checked two ways: against
   the code objects CPython compiles from the same source (`pipeline/tests/test_l2_resolve.py`,
   the corpus and seven standard-library modules; the differences L1 makes on purpose, PEP 709's
   inlined comprehensions, PEP 695 scopes and unlowered `async` bodies, are named and skipped), and
   against the host's code objects for the translated code (eval2, below). Building it found four
   rules of CPython's that a reading of `symtable.c` alone would have missed: `co_varnames` puts
   keyword-only parameters before `*args`; `co_cellvars` lists cell parameters first, in
   parameter order; a `try` statement's `else` block comes before its handlers in the order of
   first appearance; and a function that loads the name `super`, with or without arguments, uses
   `__class__`. It also found that the frontend marked a PEP 563 module's `__annotate__`
   functions as reading the class namespace, which CPython's do not (they evaluate only strings).
2. `to-anf` (`pipeline/l2/lower.py`): expressions flattened into temporaries in Python's
   evaluation order, every operation named. The draft's `protocol-ops` is part of it: an ANF
   statement is one named operation, so there was nothing left for a separate pass to do. Calls,
   displays and dict displays are built in the order CPython's code generator builds them, step
   for step as `eval1` does.
3. `lifetimes` (`pipeline/l2/lifetimes.py`): the releases of section 5 by backward liveness.
4. Later, an L2-to-L2 pass for generators: `yield` lowered to a state machine (design section
   10.3 chose a state-machine lowering of our own over C++ coroutines).

`eval2` (`pipeline/l2/eval2.py`) translates each code object into a host Python function and runs
it, statement for statement. Temporaries are host locals that `Release` deletes, so the host's
reference counting runs a finaliser at the `Release` that drops the last reference. The exception
edge is generated code: around every `Try` body and every function body, an `except BaseException`
sets the region's temporaries to None, newest first, and re-raises, so they die before any handler
while the frame's locals stay with the traceback. Local, cell and free variables are the host
function's own; the host compiler derives their kinds again from the generated code, and eval2
checks that its code objects have exactly L2's slot tables in L2's order (`SlotMismatch`).
Global, name and classdict accesses go through one helper object per module, reached as a closure
variable, so the generated functions' globals are the module's namespace and nothing else: C code
that reads the calling frame's globals sees the program's module. A translation rather than an
interpreter loop keeps the host from holding references of its own between statements (the
hygiene section 5 asks for comes from the structure: there is no loop with locals to leak), and
runs the corpus in about 20 seconds.

Status (2026-11-02): `make eval2-corpus` passes 62 of the 75 corpus cases, every case `eval1`
passes plus three (`locals()` in a function, PEP 667, among them), the lifetime cases C-9, C-3-01
and C-3-12 included. `make targets-eval2`: the easy three print their recorded output under eval2,
each with its whole closure (about 110 modules lowered to L2 and compiled before the program
starts, as P-1 does for L1; staged texts replayed by the site the calling code object names; a
function the staging refused or the lock lists as unsupported compiled to a refusal). The
checking mode (`eval2.Interpreter(audit=True)`) audits every release: if the object survives, no
local of the translation's own may hold it. Running frames are walked, since they have no frame
object for `gc.get_referrers` to find; suspended generators are found through it. Built-in
immutables are skipped, because they share identity by value and have no finaliser. The release-point
probes run under it in `make test`, with no finding.

## 8. Decisions (the author, 2026-11-02)

The six questions of v0, answered one at a time; each answer was asked with the measurement or the
code that bears on it, and `docs/DECISIONS.md` records them.

1. **Release points are statements.** One mechanism for every death: after an operation, at a
   `store`, at a loop's exit, across `g += f()`. The emitter fuses `op; release t3; release t2`
   into a call that takes its operands by move only where that matches the operation's own drop
   order, and writes the releases out otherwise. The exception edge is a rule, not statements: the
   live temporaries die newest first, before the handler runs, which is what C++ unwinding does to
   automatic objects. Rejected: a "consumed" mark on operands, shorter, but it needs statements
   for the deaths that are not at an operation anyway, and it hides the order.
2. **`eval2` checks lifetimes on host objects, with the hygiene of section 5** (a
   `gc.get_referrers` checking mode, explicit unwinding, a probe per kind of release point).
   Rejected: running L2 on the reference model, which would check every count but means running
   the standard library on a second runtime, and buys only what the hygiene buys (no reference
   held by `eval2` itself can hide a misplaced release). The model's job stays `object.hpp`'s own
   test (task 3).
3. **Types: the slot only.** Every place has a `type` field, always `object` in phase 1. A declared
   type cannot change what a program does in phase 1: `x: int` admits `bool` and subclasses that
   override operators, which strict mypy accepts (`class Loud(int)` with a printing `__mul__`
   passed to `def double(x: int) -> int: return x * 2` prints from `__mul__`). By L1 the static
   annotations are gone anyway (`desugar-function-annotations` turns them into `__annotate__`).
   The gap to the design's level table is marked (section 1) and closes in phase 2, with the
   oracle and the passes that can use its types, behind `Fact.TYPES`. Rejected: declared types
   carried inert through the fourteen frontend passes, for comments in the C++; mypy's types now,
   mapped back to `ast` nodes, for a stdlib that is mostly unannotated.
4. **Exceptions are C++ exceptions** (design section 12 had decided it for modules). Measured in
   the image: a C++ throw and catch costs about 1.7 µs (one frame) to 2.3 µs (three), CPython's
   raise and catch about 0.18 µs to 0.47 µs, an error return 2 ns. So the runtime never throws for
   a miss it expects, as CPython's C code does not raise for them: `for_next` returns an end
   marker, and `getattr` with a default, `hasattr`, `dict.get`, `next` with a default and `in`
   use sentinels. A throw happens only where the program raises or an operation fails, and a
   phase-2 pass rewrites the common idioms (`try: x = d[k] except KeyError:` into a lookup that
   reports absence). Rejected: error returns everywhere, cheap to raise, but a check and an exit
   after every operation (about 5 %, more code, C++ noisier than the L2 it comes from), and
   libstdc++ still throws.
5. **Frames: a record and a guard, exact.** Each function has a record on the C++ stack: its
   code descriptor (name, file, slot names) and the current line, which L2's `line n` stores. A
   guard declared after the locals, so destroyed first when unwinding, appends `(code, line)` to
   the exception's traceback and moves the locals into that entry, so they die with the
   traceback as in CPython (`buf` in a raising `parse()` dies at `del saved` when the handler kept
   the exception, measured). No CPython frame objects: E-02 stays. Rejected: letting the locals
   die during unwinding, which breaks section 9 of the spec and could not be linted precisely.

   ```cpp
   Obj parse() {
       Local buf;
       FrameGuard g(code_parse, buf);     // after the locals: destroyed first when unwinding
       g.line = 5; buf = py::call(O, S_buf);
       g.line = 6; throw py::raise(ValueError, S_bad);
   }   // unwinding: g appends (parse, 6) to the traceback and takes buf with it
   ```
6. **Module globals: no glue pass in phase 1.** Each module keeps a dict, and every global read
   site caches the dict's key version and an index, with the builtins' version for the fallback,
   as CPython's `LOAD_GLOBAL_MODULE` does. The author's whole-program pass, gluing every module's
   globals into fields of one application object, comes in phase 2 as an L2-to-L2 pass after
   `resolve-names`, with the module's dict as a *view* over the fields, not a dict the fields
   migrate into on exposure: 15 modules of the closure expose their own globals (`os`'s
   `name in globals()`, `hashlib`'s `globals()[name] = ...`, `typing`, `types`, and `re`,
   `calendar` and `signal` through `enum.global_enum`), and `dataclasses.py` line 1011 takes
   `sys.modules[cls.__module__].__dict__` for every class it processes. The view keeps the dict's
   insertion order (`del x` then `x = 3` moves `x` after `y`) and its mutation counter (binding a
   global while `globals()` is iterated raises `RuntimeError`), and goes into
   `refmodel/objects.py` first, as a kind of object of its own for modules.
